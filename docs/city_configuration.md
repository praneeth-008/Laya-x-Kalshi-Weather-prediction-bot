# City Configuration: NYC (current, and only, target)

## Current NYC target (from actual project configuration/code)

- **City**: New York City
- **Primary observation station**: KNYC / Central Park, ISD station id `725053-94728` (`data/observations.py`)
- **Auxiliary observation stations** (predictors only): KLGA (`725030-14732`), KJFK (`744860-94789`), KEWR (`725020-14734`)
- **Timezone**: `America/New_York` (`NYC_TZ`, defined independently in `data/hrrr.py`, `data/gfs.py`, `data/weather_state.py` -- see the duplication note below)
- **Forecast target coordinates**: lat `40.7794`, lon `-73.9691` (`CENTRAL_PARK` dict, defined independently in `scripts/pilot_phase3_hrrr.py`, `scripts/pilot_phase3b_hrrr_apcp_1h.py`, `scripts/pilot_phase4_gfs.py`). Sourced from the `isd-history.csv` registry record for station `725053-94728` (per `config/bulk_download_spec.json`).
- **Numerical-model grid/patch**: 3x3 patch, +/-0.03deg offsets around the target coordinates, requested identically for every numerical source (see `data_sources.md` for how this resolves very differently for HRRR's ~3km grid vs. GFS's 0.25deg grid).
- **NWS office / AFD product**: OKX / AFDOKX (`scripts/pilot_phase2_afd.py`).
- **Kalshi series**: `KXHIGHNY` (`data/kalshi.py`) -- the daily NYC maximum-temperature market.
- **Target variable**: daily maximum temperature.

## Forecast target vs. Kalshi settlement mechanism -- kept explicitly separate

**Central Park / KNYC observed daily max temperature is the forecast target used throughout weather extraction. It is not automatically assumed identical to the Kalshi settlement value for `KXHIGHNY`.** This is a standing, deliberate decision recorded in `config/bulk_download_spec.json`: `"trading_settlement_target": "NOT DEFINED HERE -- explicitly out of scope; Central Park observed Tmax is not assumed identical to any historical Kalshi settlement value"`. As of this documentation phase, the actual Kalshi settlement mechanism/source for `KXHIGHNY` has not been investigated or documented -- `data/kalshi.py` only implements historical market/event *discovery*, not settlement-value retrieval or verification. This must be resolved and separately audited before any model output is compared against or evaluated using Kalshi outcomes.

## Hard-coded NYC assumptions found (inventory only -- not refactored)

A repository-wide search found NYC-specific literals (`40.7794`/`-73.9691`, `America/New_York`, `KNYC`/`KLGA`/`KJFK`/`KEWR`, `OKX`/`AFDOKX`, `KXHIGHNY`) appearing directly in **30 Python files** -- essentially the entire `data/` and `scripts/` tree. `config.py` exists but is currently an empty placeholder (its own docstring says it "will eventually hold" this kind of configuration -- it does not yet). Concretely, before a second city could be added, at minimum the following would need to become configuration rather than literals:

1. `CENTRAL_PARK` / target coordinates -- duplicated identically across 3 pilot-phase scripts.
2. `PATCH_OFFSETS` -- duplicated identically across the same 3 scripts.
3. `NYC_TZ` -- duplicated across `data/hrrr.py`, `data/gfs.py`, `data/weather_state.py` (each defines its own `ZoneInfo("America/New_York")`).
4. `STATIONS` list in `data/observations.py` (station ids, ICAO codes, lat/lon, elevation).
5. AFD office/product (`OKX`/`AFDOKX`) in `scripts/pilot_phase2_afd.py`.
6. `SERIES_TICKER = "KXHIGHNY"` in `data/kalshi.py`.
7. `SELECTED_DATES` source path (`data/processed/weather/pilot/selected_days.csv`) -- currently a single fixed path, would need to be per-city.
8. Output/checkpoint directory paths (`data/processed/pilot/{hrrr,gfs,hrrr_apcp_1h}/`) -- currently fixed, would need a city segment.

## Proposed future city-config schema (design only -- not implemented)

Derived from the actual parameters found above, not invented from scratch:

```yaml
city: "nyc"
timezone: "America/New_York"

target:
  station: "KNYC"          # ISD station id: 725053-94728
  latitude: 40.7794
  longitude: -73.9691
  variable: "daily_max_temperature_f"
  patch_offsets_deg: [-0.03, 0, 0.03]   # applied as a 3x3 grid around (latitude, longitude)

observations:
  primary_station: "KNYC"
  auxiliary_stations: ["KLGA", "KJFK", "KEWR"]

weather_grid:
  hrrr:
    max_patch_distance_km: 10.0
  gfs:
    max_patch_distance_km: 20.0
  nbm: {}      # not yet extracted for any city; thresholds/fingerprints TBD
  gefs: {}
  ecmwf: {}

nws:
  office: "OKX"
  afd_product: "AFDOKX"

kalshi:
  series_ticker: "KXHIGHNY"
  settlement_metadata: null   # UNRESOLVED -- see "Forecast target vs. Kalshi settlement mechanism" above; must be filled in and separately audited, not assumed equal to the observation station
```

Everything under `weather_grid` beyond the per-source distance threshold (grid fingerprints, explicit product-selection rules, temporal semantics) is **source-specific, not city-specific** -- a new city reuses the same HRRR/GFS extraction code and the same product-selection logic, but will very likely have a **different grid fingerprint** (different nearest grid cell) and should **re-derive its own distance threshold and re-run the validation checklist** (`validation.md`) rather than assuming NYC's values transfer. The `extraction_runbook.md` procedure exists precisely so this re-validation is systematic rather than skipped.
