# Reproducibility & Versioning

Goal: months later, be able to answer precisely "what information did model version X see, and exactly how was that information produced?" This requires versioning more than just the model checkpoint.

## What must be versioned for a reproducible experiment

| Item | Current state in this repo |

## Dataset manifest schema

Each frozen source pilot gets a `manifest.json` at `data/processed/pilot/{source}/manifest.json` (`.gitignore` allows exactly this one file per source directory through; the checkpoint, download report, and Parquet parts stay untracked). Fields:

```
manifest_version, dataset_name, dataset_status, manifest_written_at_utc
provenance:
    git_commit, git_commit_short, git_branch,
    working_tree_clean_at_extraction, provenance_status ("exact" | "historical provenance partially reconstructed"),
    notes   # required whenever provenance_status is not "exact" -- state plainly what is/isn't verifiable, never guess
target: city, station, latitude, longitude, timezone
selected_days: path, count, sha256
source: name, variables, grid_fingerprint, max_patch_distance_km, availability_method, temporal_semantics_reference
work_items: planned, done, failed, row_count, parquet_part_count   # (+ source-specific fields, e.g. HRRR APCP_1H's fh=0 exclusion count)
paths: checkpoint, processed_data, download_report
extraction_script
runtime_overrides   # any parameter used at run time that differs from the committed script's own default -- record honestly, never omit
validation: status, references
```

**On `provenance_status`**: use `"exact"` only when the working tree was verifiably clean at the commit recorded (i.e. the committed code is provably what ran). Otherwise use `"historical provenance partially reconstructed"` and explain in `notes` exactly what is known and what is inferred from session history rather than from git itself -- this happened for both the HRRR APCP_1H backfill and part of the GFS pilot (see their manifests for the actual wording used).

## Present reproducibility gaps (remaining after this phase)

1. ~~No single manifest links a processed-data directory to the exact git commit that produced it.~~ **Closed** by the manifest schema above -- see the three existing manifests.
2. **Selected-day manifest versioning.** `selected_days.csv` is a derived artifact (from observations data via a systematic-sampling script), but is currently treated as a fixed input by the pilot scripts. Each dataset manifest now records its SHA-256, which gives drift *detection* (compare hashes across manifests), but there is still no automatic *enforcement* that a re-run used the same file.
3. **City/source configuration is not yet externalized** (see `city_configuration.md`) -- "which config produced this data" currently means "which commit," which is coarser than ideal once multiple cities exist.
4. **Manifests are generated after the fact, not automatically by the extraction scripts themselves.** `extraction_runbook.md`'s mandatory manifest rule establishes the process going forward, but no code currently auto-generates a manifest as part of `write_report()`. Until that exists, manifest creation is a manual step that could be forgotten.

## What IS already reliably reproducible today

- Given a specific git commit and the existing checkpoint files, re-running a phase script will deterministically skip everything already `DONE` and only attempt what's missing (`Checkpoint.is_done()`), so partial re-runs are safe and reproducible.
- The exact work-item universe for a given source/city/selected-day-list is deterministically recomputable from code alone (verified repeatedly this session: independently recomputed HRRR's 20,836 and GFS's 5,836 work items from scratch and confirmed exact matches against the live checkpoints).
- Grid fingerprints, distance thresholds, and explicit selection rules are all recorded in `variable_semantics.md`/`data_sources.md` and can be re-verified against a fresh extraction at any time.
